# Shin4Static — дизайн

Маршрутизация выбранных сетей через VPN на роутере Keenetic (Entware) по
пользовательским спискам, с kill switch для отдельных записей.

Проект вырос из разбора Bird4Static, но написан заново: из Bird4Static
взята только идея (BIRD + iprange + cron), код не заимствован.

## Что убрано по сравнению с Bird4Static

- скачивание больших списков (antifilter и т. п.) и BGP-режим;
- подстановка настроек в скрипты через `sed` — настройки живут в одном
  конфиге, скрипты его читают;
- `diff | patch` для обновления файлов — вместо него `cmp` + `mv`;
- RADB как источник префиксов AS (данные IRR бывают устаревшими и чужими).

## Списки

`/opt/etc/shin4static/lists/`:

| Файл        | Основной выход |
|-------------|----------------|
| `isp.list`  | провайдер      |
| `vpn1.list` | VPN1           |
| `vpn2.list` | VPN2 (если настроен) |

Одна запись на строку: IPv4, подсеть `a.b.c.d/nn`, диапазон `a.b.c.d - e.f.g.h`,
домен или `AS<номер>`. Комментарии — `#` или `;` (в начале строки или после
записи через пробел).

Отключённая запись — `#off ` в начале строки (`#off !KS0 AS13335  # офис`). Для
генератора это обычный комментарий, поэтому ничего в нём не меняется; веб
показывает такую строку записью с кнопкой «вкл», `check`/`update` сообщают их
число, `why` показывает подходящие отключённые записи с пометкой. Адреса
отключённого домена при следующем `update` забываются, как у удалённого.

Перед записью может стоять метка — что делать, если основной выход недоступен:

| Метка   | Цепочка |
|---------|---------|
| нет     | основной → провайдер (через таблицу main) |
| `!KS0`  | основной → блок |
| `!KS<n>`| основной → VPN<n> → блок |
| `!FB<n>`| основной → VPN<n> → провайдер |

`n` — номер VPN (1 или 2), не совпадающий с основным выходом. Неизвестная
метка или ссылка на ненастроенный VPN — ошибка строки (строка пропускается,
остальной список работает).

## Таблицы маршрутизации: по шагу цепочки, а не по интерфейсу

| Приоритет `ip rule` | Таблица ядра | Содержимое |
|---|---|---|
| 30031 | 1031 (шаг 1)  | каждая сеть — через свой основной выход |
| 30032 | 1032 (шаг 2)  | сети с `!KS<n>`/`!FB<n>` — через резервный VPN |
| 30039 | 1039 (блок)   | сети с `!KS…` — `unreachable` |
| 32766 | main          | всё остальное, провайдер |

Маршрут через упавший интерфейс снимается (BIRD снимает static-маршрут через
интерфейс, ядро — маршруты на выключенном интерфейсе), и поиск переходит к
следующему правилу. Номера таблиц и приоритеты меняются в конфиге; по
умолчанию они не пересекаются с Bird4Static (1020–1022, 30020–30022). Если
номера поменять, при следующем `update` (или `rules start`) старые правила и
таблицы убираются: применённые номера записаны в `/opt/var/shin4static/applied`.

Не пересекаются номера, но не адреса: правила с меньшим приоритетом (Bird4Static,
политики Keenetic) проверяются раньше, и адрес, попавший в их таблицу, до
наших не доходит — ни маршрут через VPN, ни kill switch. `shin4static status`
перечисляет такие правила.

### Пересечения

Внутри одной таблицы ядро выбирает самый точный маршрут. Если узкая сеть с
`!KS0` и широкая без метки лежат в одной таблице, то при падении выхода узкой
сети трафик уйдёт по маршруту широкой — kill switch не сработает. Поэтому
каждый адрес принадлежит ровно одной группе. Группы обрабатываются по
старшинству: сначала всё из `isp.list` (явные исключения — например, адрес
VPN-сервера), затем `!KS0`, `!KS<n>`, `!FB<n>`, без метки; при равенстве vpn1
раньше vpn2. Из каждой следующей группы вычитаются адреса предыдущих
(`iprange --exclude-next`). О каждом пересечении выдаётся предупреждение.

## Надёжность

- Ошибка в одной строке не ломает список (в отличие от поведения iprange 2.x):
  строки проверяются до iprange, домены резолвятся по одному.
- Адреса каждого домена запоминаются (`/opt/var/shin4static/dns/`): если
  домен не разрезолвился (DNS лёг или не ответил только на это имя), берутся
  его прежние адреса с предупреждением, а не выпадают до следующего часа.
  Ответы 0.0.0.0 и 127.x (так DNS-фильтры отвечают на заблокированные имена)
  не берутся. Готовность DNS проверяется по нескольким именам.
- Префиксы AS кэшируются (по умолчанию на сутки), при недоступности
  источников берётся устаревший кэш. Ответ, оборванный по таймауту или
  разрывом связи (curl вернул ошибку), не принимается. Из префиксов AS
  выкидываются частные и служебные сети и слишком широкие префиксы.
- Октеты с ведущим нулём (`010.0.0.1`) — ошибка строки: iprange читает их как
  восьмеричные и молча взял бы другую сеть.
- Если iprange не работает или упал на любом шаге, прогон останавливается и
  маршруты не трогаются. Файл маршрутов с группой без единого маршрута не
  ставится никогда.
- Блокировка от двойного запуска (занято — код 75, веб пишет «повторите»),
  таймауты у curl, ожидание DNS ограничено.
- Новые файлы маршрутов проверяются `birdc configure check`; при ошибке, как и
  при неудачном `configure`, возвращаются прежние.
- BIRD перезагружается только если маршруты действительно изменились.
- `update` восстанавливает пропавшие `ip rule` и запускает упавший BIRD.
- `ISP_GW=auto`: найденный шлюз провайдера запоминается; если сейчас шлюза
  нет (сразу после загрузки, провайдер упал), берётся прежний.
- Остановка (`rules stop`, `daemon stop`, `flush`) работает и с испорченным
  конфигом: значения по умолчанию и номера, применённые в прошлый раз.

## Независимость от системного bird и Bird4Static

Shin4Static запускает свой экземпляр BIRD и не трогает системный:

- `bird` и `birdc` копируются при установке в `/opt/share/shin4static/sbin/`
  под именами `s4s-bird`/`s4s-birdc`. Имя процесса другое, поэтому
  `killall bird`, `S70bird stop|restart` и `killall -s SIGHUP bird` (так
  Bird4Static перечитывает свой конфиг) его не задевают; удаление пакета
  `bird2` копии не удаляет.
- Свой конфиг `/opt/etc/shin4static/bird.conf`, свой управляющий сокет
  `/opt/var/run/shin4static-bird.ctl`. `/opt/etc/bird.conf` не читается и не
  меняется.
- Свои таблицы (1031/1032/1039) и приоритеты (30031/30032/30039), имена
  файлов не попадают под маски Bird4Static (`/opt/etc/bird*`, `bird4*.list`).
- Kernel-протоколы с `persist`: если BIRD Shin4Static остановлен или упал,
  маршруты (и kill switch) остаются в ядре. Удаляет их только `shin4static
  flush` (его вызывает uninstall.sh).

Команды `ip` с таблицами выше 255 прошивочный `ip` не понимает, поэтому
ставится `ip-full`, и скрипты вызывают `/opt/sbin/ip`.

## Ограничения (осознанные)

- Только IPv4. Домены и AS дают IPv4-префиксы, IPv6 отбрасывается, правил
  `ip -6 rule` нет. Если провайдер выдаёт IPv6, клиенты ходят по IPv6 мимо
  VPN и мимо `!KS…`; IPv6 для клиентов лучше выключить.

- Домены резолвятся с роутера раз в час: CDN могут выдавать клиентам другие
  IP. Для доменов с поддоменами и точными IP нужен подход ipset+dnsmasq.
- Правила `ip rule` без условий по источнику: действуют и на трафик самого
  роутера. Адрес VPN-сервера нельзя ставить под `!KS…` (иначе упавший туннель
  не поднимется); его лучше держать в `isp.list`.
- WireGuard-интерфейс остаётся поднятым, когда сервер не отвечает: трафик
  уходит в мёртвый туннель (утечки нет, но и переключения тоже). Для
  переключения включите в Keenetic проверку доступности у подключения.

| `/opt/var/run/shin4static-bird.ctl`, `.pid` | сокет и pid своего BIRD |

## Веб-интерфейс

CGI на sh (`www/cgi-bin/s4s`) и одна страница без внешних библиотек; формат
файлов списков не меняется. Сервер — свой экземпляр lighttpd по той же схеме,
что и BIRD: переименованная копия `s4s-lighttpd` (обновляется при каждом
запуске, чтобы совпадать с модулями пакета), свой конфиг
`/opt/etc/shin4static/lighttpd.conf` (собирается из `shin4static.conf` при
старте), свой порт и pid. Так его не задевают ни `S80lighttpd`, ни остановка
процессов по имени `lighttpd` (на Keenetic так называется и WebDAV-сервер
прошивки). Если lighttpd ставится только ради Shin4Static, автозапуск
стандартного выключается. busybox httpd на Keenetic нет.

Вход, `WEB_AUTH=router`: пароль от веб-интерфейса роутера, по схеме страницы
входа Keenetic. CGI делает `GET /auth` (`X-NDM-Realm`, `X-NDM-Challenge`),
хранит cookie роутера под одноразовым id и отдаёт realm и challenge странице.
Браузер считает `sha256(challenge + md5(логин:realm:пароль))` сам (свои MD5 и
SHA-256 в `hash.js`: на HTTP-странице по IP WebCrypto недоступен) и
отправляет только хеш; CGI передаёт его в `POST /auth`, роутер отвечает 200
при верном пароле, сессия на роутере сразу закрывается (`DELETE /auth`).
Дальше — своя сессия: случайный id в cookie (`HttpOnly`, `SameSite=Strict`),
файл в `/opt/var/shin4static/web-sessions/`, срок по бездействию. Пароль нигде
не сохраняется и по сети не передаётся. Попытки входа идут по одной для всех
клиентов, после трёх неверных паролей каждая ждёт на 30 с дольше (до 10 минут).
lighttpd в этом режиме без mod_auth: страница открыта, данные отдаёт только CGI
с сессией.

Режим входа CGI берёт не из `shin4static.conf`, а из `web.mode`, который пишет
`S81shin4static-web` при запуске lighttpd. Иначе правка `WEB_AUTH` без
перезапуска (или строка, которую sh и sed читают по-разному) оставила бы
страницу без пароля вовсе: lighttpd без mod_auth, CGI без сессий. Нет файла —
CGI отказывает; режим `local` без пользователя от lighttpd — тоже.

Изменяющие запросы (и вход) принимаются только со своей страницы: заголовки
`Origin` и `Sec-Fetch-Site`. `WEB_ALLOW` проверяет и сам lighttpd
(`url.access-deny` для остальных адресов), размер запроса ограничен
(`server.max-request-size`), чтобы большим POST нельзя было занять память
роутера. Сохранение передаёт `base` — MD5 текста, загруженного страницей; если
файл с тех пор изменился, CGI отказывает.

`WEB_AUTH=local`: свой пароль в формате htdigest
(`md5(admin:Shin4Static:пароль)`, получается `md5sum`, без openssl); lighttpd
принимает такой файл и для Basic-авторизации.
